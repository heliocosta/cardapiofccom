# Requirements Document

## Introduction
CardápioFC is moving from a Brazil-only football TV guide to a worldwide site with six regional editions. This feature (site-foundation) delivers the base every other spec builds on: a repaired, upgrade-safe site configuration; a single edition registry; localised interface strings and date/time formatting; removal of demo content and unused outputs; a redesigned, mobile-first visual system with shared page shells and components; named extension slots for downstream features; and consistent build tooling.

Primary actors: **visitors** (read the site in their edition), the **site operator** (configures editions, runs builds, updates the theme) and **downstream spec implementers** (data-pages, app-deeplinks, seo-social, edge-delivery, analytics-consent) who consume the contracts this feature stabilises.

Terms: the **Site Build** is the project's standard development/production build; the **Site Build check** is the automated verification the operator runs after a production build to confirm these requirements; the **Repository** is the project's version-controlled source tree.

## Boundary Context
- **In scope**: configuration repair; edition registry and per-edition content folders; interface strings (English, Portuguese, Spanish + regional wording); localised date/time display; menus; demo cleanup and disabling unused page kinds/outputs; design tokens, light/dark mode; header, edition switcher, footer; home, list and detail page shells; per-edition 404 page; match card, team crest, channel badge and date group components; extension slots; build tool version consistency and a single lock file.
- **Out of scope**: fetching remote data and generating league/team/match/lineup pages (data-pages); meta descriptions beyond a basic fallback, canonical, hreflang tags, Open Graph, structured data, sitemaps, robots, llms.txt (seo-social); analytics, tag manager, consent banner, privacy policy text (analytics-consent); zero ads (the site will have no advertisements); search, app landing pages, smart app banner, well-known files (app-deeplinks); hosting, CI deploy workflow, geo-routing and legacy redirects (edge-delivery).
- **Adjacent expectations**: downstream features render their pages with this feature's components and shells and add their own head/body/footer output through the extension slots and their own menu entries, without editing files this feature owns. Downstream features supply match, team and channel data in the shape the components document; this feature never fetches data.

## Requirements

### Requirement 1: Site configuration repair and upgrade safety
**Objective:** As the site operator, I want a valid, complete configuration that survives theme and module updates, so that every build is reliable and the project stays upgradeable.

#### Acceptance Criteria
1. When the production build command is run on a clean checkout, the Site Build shall complete without errors and produce output for all six editions.
2. The Site Build shall use a configuration that contains, in valid form, every site-wide setting lost from the broken configuration: base URL, theme, output formats, module mounts, build statistics, permalinks, plugin lists and the analytics service placeholder.
3. When the development or production build command runs, the Site Build shall regenerate the theme stylesheet tokens from the theme data file without errors.
4. The Repository shall keep the vendored theme directory and the vendored module directory unchanged by this feature, except for files regenerated by the project's standard scripts.
5. When the theme update command is run after this feature is delivered, the Site Build shall still complete without errors and the site shall keep all CardápioFC customisations.
6. The Site Build shall keep all six editions active and shall not depend on the multilingual-removal script.

### Requirement 2: Edition registry
**Objective:** As the site operator, I want one registry that defines every edition, so that edition behaviour is consistent everywhere and new editions need no template work.

#### Acceptance Criteria
1. The CardápioFC Site shall provide exactly six editions at launch: Global (`en`), United Kingdom (`en-gb`), Ireland (`en-ie`), Brazil (`pt-br`), Portugal (`pt-pt`) and Argentina (`es-ar`).
2. The CardápioFC Site shall record for each edition: a lowercase edition code, a BCP 47 locale (for example `en-GB`), an ISO 3166-1 alpha-2 country code (none for Global), an IANA time zone, a URL prefix, an hreflang value, a base interface language, a localised edition name, a site title, a site description and a time-zone label.
3. The CardápioFC Site shall serve the Global edition at the site root without a prefix and every other edition under `/{edition-code}/`.
4. The CardápioFC Site shall declare the edition's BCP 47 locale as the document language of every page.
5. If an edition record is missing a required value or contains an invalid value (unknown time zone, locale that does not correspond to the edition code, country code on Global or missing on a regional edition), then the Site Build shall fail with a message naming the edition and the offending field.
6. When the site operator adds a new edition whose base interface language already exists, the CardápioFC Site shall build and serve that edition after configuration changes only, without changes to any template, component or stylesheet.
7. When the site operator adds a new edition with a new base interface language, the CardápioFC Site shall build and serve that edition after configuration changes and one new interface-string file only.
8. The CardápioFC Site shall derive every edition-dependent output it renders (language, time zone, labels, prefixes, titles) from the registry, so that changing a registry value changes all affected pages on the next build.

### Requirement 3: Content structure, demo removal and unused outputs
**Objective:** As the site operator, I want a clean content tree per edition without demo material or unused pages, so that the site publishes only CardápioFC content and stays small.

#### Acceptance Criteria
1. The CardápioFC Site shall keep each edition's content in a separate content folder named after the edition code.
2. The CardápioFC Site shall publish a home page for each edition at the edition's root URL.
3. The CardápioFC Site shall not publish any demo material: blog posts, authors, testimonials, the elements page, demo about/contact pages, demo sections or the demo content-management configuration.
4. The CardápioFC Site shall not generate taxonomy pages, term pages, RSS feeds or per-page Markdown copies.
5. The CardápioFC Site shall not generate a redirect page at `/en/` for the Global edition.
6. The CardápioFC Site shall not include stock theme features that have no CardápioFC purpose (demo search modal, preloader, announcement bar, testimonial slider, gallery, comments) in any published page.

### Requirement 4: Localised interface strings
**Objective:** As a visitor, I want all interface text in my edition's language and regional wording, so that the site feels native to my country.

#### Acceptance Criteria
1. The CardápioFC Site shall provide interface strings in English, Portuguese and Spanish.
2. Where an edition's regional wording differs from its base language (for example "equipa" in Portugal versus "time" in Brazil, "fixtures" and "kick-off" in the United Kingdom), the CardápioFC Site shall show the regional wording on that edition only.
3. If a regional wording is not defined for a string, then the CardápioFC Site shall show the string from the edition's base interface language and never from another language.
4. If an interface string is missing from any base-language file, then the Site Build check shall fail and list each missing string key and language.
5. The CardápioFC Site shall render every user-visible text in the pages, shells and components delivered by this feature from interface strings or registry values, with no hard-coded text in a single language.

### Requirement 5: Localised date and time display
**Objective:** As a visitor, I want kick-off times and dates shown in my edition's time zone with the zone stated explicitly, so that I never miss a match because of a mislabelled time.

#### Acceptance Criteria
1. When the CardápioFC Site displays a time supplied in UTC, it shall convert that time to the edition's time zone.
2. The CardápioFC Site shall display an explicit zone indicator next to every displayed kick-off time, consisting of the edition's time-zone label and its UTC offset for that date, and shall never label a time as "local" without naming the zone.
3. The CardápioFC Site shall format day names, month names and date order according to the edition's locale.
4. The CardápioFC Site shall attach a machine-readable timestamp including the UTC offset to every displayed date or time.
5. While daylight saving time is in effect in an edition's time zone on the displayed date, the CardápioFC Site shall apply that date's correct UTC offset.
6. Where the edition is Global, the CardápioFC Site shall display times in UTC labelled "UTC".
7. If a supplied time value has no explicit UTC designator or offset, then the Site Build shall fail with a message naming the value.
8. When items are grouped by day, the CardápioFC Site shall assign each item to the calendar day on which it occurs in the edition's time zone.

### Requirement 6: Header, navigation, edition switcher and footer
**Objective:** As a visitor, I want consistent navigation and an easy way to switch edition, so that I can move around the site and pick the edition that suits me.

#### Acceptance Criteria
1. The CardápioFC Site shall show on every page a header containing the logo linked to the current edition's home, the edition's main menu, the edition switcher and the light/dark mode control.
2. When a visitor chooses another edition in the edition switcher, the CardápioFC Site shall take the visitor to the equivalent page in that edition if it exists, otherwise to that edition's home page.
3. When a visitor chooses the Global edition in the edition switcher, the CardápioFC Site shall include an explicit edition-choice marker in the destination address so that downstream routing can distinguish a manual choice from an automatic one.
4. The edition switcher shall list every edition by its localised edition name, indicate the current edition, and be fully operable by keyboard and screen readers with JavaScript disabled.
5. The CardápioFC Site shall show menu labels in the edition's language.
6. When another feature's page declares itself a member of the main or footer menu, the CardápioFC Site shall show it in that edition's menu without changes to the menu configuration owned by this feature.
7. If an edition has no main menu entries, then the CardápioFC Site shall render the header without an empty menu list.
8. The CardápioFC Site shall show on every page a footer containing the edition's copyright notice, the edition's footer menu and links to the home page of every edition.

### Requirement 7: Visual design system
**Objective:** As a visitor, I want a modern, readable, mobile-first design in light or dark mode, so that the site is pleasant and accessible on any device.

#### Acceptance Criteria
1. The CardápioFC Site shall take all brand colours (light and dark), font families and the type scale from a single theme data file, so that changing a token there changes every page without template edits.
2. The CardápioFC Site shall offer light, dark and system-following colour modes and remember the visitor's choice across visits.
3. The CardápioFC Site shall lay out every page delivered by this feature without horizontal scrolling at viewport widths from 320 CSS pixels upward.
4. The CardápioFC Site shall meet WCAG 2.2 AA colour contrast for text and interactive elements in both light and dark modes.
5. The CardápioFC Site shall give every interactive element a target size of at least 24 by 24 CSS pixels and a visible keyboard focus indicator.
6. While the visitor's system requests reduced motion, the CardápioFC Site shall not play non-essential animations or transitions.

### Requirement 8: Shared UI components
**Objective:** As a downstream spec implementer, I want ready-made match, crest, channel and date-group components, so that every page shows matches consistently, quickly and accessibly.

#### Acceptance Criteria
1. When given a match, the match card shall show both team names with crests, the kick-off time in the edition's time zone with its zone indicator, the league name when supplied, the match status, and a link to the match page address supplied with the match.
2. When a match status is live or finished and a score is supplied, the match card shall show the score.
3. When a match status is postponed or cancelled, the match card shall show the localised status in place of the kick-off time.
4. When a match card is asked to show broadcasters and the broadcaster list is empty, the match card shall show the localised "no broadcaster listed — check the app" message.
5. The team crest shall show the crest image with the team name as its text alternative, except where the team name is already shown as adjacent visible text, in which case the crest shall be hidden from assistive technologies to avoid repetition.
6. If no crest image address is supplied or the crest image fails to load, then the team crest shall show the team's initials in a placeholder of the same size.
7. The team crest and channel badge shall reserve their display size before images load so that the page layout does not shift, and shall defer loading of images outside the first screen.
8. The channel badge shall show the channel name, its logo when supplied and a localised channel-type indicator.
9. Where a channel address is supplied, the channel badge shall link to it and open it in a new browsing context without giving the destination access to the opener.
10. The date group shall show a localised heading for the calendar day in the edition's time zone followed by that day's matches in kick-off order.
11. The match card, channel badge and edition switcher shall expose stable, documented data attributes identifying the interaction (match open, channel click, edition switch) and the edition, and shall contain no tracking code.
12. If an optional component input is absent, then the component shall omit the related element without rendering empty containers or placeholder text such as "undefined".

### Requirement 9: Page shells and error page
**Objective:** As a visitor, I want every page type to share one coherent layout, and as a downstream implementer I want shells I can fill, so that pages look consistent without duplicated layout code.

#### Acceptance Criteria
1. The CardápioFC Site shall provide for each edition a home page shell with a localised heading and introduction and a main content region that the data feature can fill.
2. If no feature has filled the home page's main content region, then the home page shall show a localised empty-state message.
3. The CardápioFC Site shall provide a list page shell and a detail page shell, each with a page title, an optional breadcrumb trail and a main content region, usable by other features without copying layout markup.
4. When a visitor requests a missing address within an edition, the CardápioFC Site shall provide a localised "page not found" page for that edition that links to that edition's home page.
5. The CardápioFC Site shall give every page a skip-to-content link, exactly one top-level heading, and header, main and footer landmarks.

### Requirement 10: Extension slots for downstream features
**Objective:** As a downstream spec implementer, I want named places to add head, body and footer output, so that SEO, analytics/consent and app features can be added without editing or competing for the same files.

#### Acceptance Criteria
1. The CardápioFC Site shall provide named extension slots in the document head, at the start of the body, at the end of the body and in the footer, with each slot assigned to exactly one downstream feature.
2. If no content has been provided for a slot, then the CardápioFC Site shall render nothing for that slot and the build shall succeed.
3. When a downstream feature provides content for its slot, the CardápioFC Site shall render that content on every page with access to the current page and edition, without the downstream feature modifying any file owned by this feature.
4. While the SEO feature has not provided its head slot, the CardápioFC Site shall still give every page a title and a meta description taken from the page or, failing that, from the edition registry.
5. The CardápioFC Site shall emit no analytics, tag-manager or consent scripts from the files owned by this feature.
6. When the data feature provides content for the home page's main content region, the CardápioFC Site shall render it inside the home page shell without the data feature modifying the home page template.

### Requirement 11: Performance budgets
**Objective:** As a visitor on a mobile connection, I want pages to load fast, so that I can check where to watch a match in seconds.

#### Acceptance Criteria
1. The CardápioFC Site shall load no more than 10 KB (compressed) of first-party JavaScript per page from this feature, and none of it shall block the first render.
2. The CardápioFC Site shall keep the combined compressed size of the HTML, first-party stylesheet and first-party JavaScript of a page shell without data content at or below 100 KB, excluding fonts and images.
3. The match card shall add no more than 2 KB of uncompressed HTML per rendered match.
4. The CardápioFC Site shall display text with fallback fonts while web fonts load, without blocking rendering.
5. The CardápioFC Site shall keep the cumulative layout shift of every page rendered with this feature's shells and components at 0.1 or less on a mobile viewport.

### Requirement 12: Build tooling consistency
**Objective:** As the site operator, I want one set of tool versions and one package manager, so that builds behave the same on every machine and CI.

#### Acceptance Criteria
1. The Repository shall pin the same site generator version (0.165.0, extended edition) and the same Go version in every retained build, CI and development-container configuration.
2. The Repository shall not contain deployment configurations for platforms that are not used (Vercel, AWS Amplify, GitLab CI).
3. The Repository shall declare a single package manager, contain only that package manager's lock file, and have every retained build configuration install dependencies with it.
4. If a retained configuration pins a site generator or Go version different from the agreed version, then the Site Build check shall fail and name the file and the mismatching version.
